# Agent Note: Harness 更新卡片报告事务的真实阶段

Status: implemented

[English](2026-09-18-harness-update-card.md)

## Problem

一次托管 Harness 事务会运行数分钟，却对桌面外壳完全不报告自身状态。启动安装、更新和重新安装的 Harness 菜单项会立即返回，事务在托管运行时自己的队列上执行，它给用户的第一个信息就是结束时弹出的那个原生对话框。注册表往返上限是 30 秒，一次包管理器运行上限是 15 分钟，而官方依赖闭包的首次解析要取回 521 个包，所以最长的合法情形看起来和一个坏掉的按钮完全一样。[托管 Harness 运行时说明](../../proposed/architecture/2026-09-10-managed-harness-runtime.md)在还没有任何界面可以承担这件事时，把它列为被接受的风险。

事务本身一开始根本不向外部报告进度。运行时为每个阶段向轮转诊断日志写一行 JSON，那是一份事后诊断用的文件，没有用户会在更新中途去打开它；而外壳对一个正在运行的事务唯一的其他了解，是一条被禁用的菜单文字。因此增加一个界面首先要决定的是能如实展示什么，而不只是展示在哪里。

## Decision

[`harness-update-view.ts`](../../../../apps/desktop/src/harness-update-view.ts) 为一次 staging 事务保存外壳侧状态：带着阶段运行、带着保留的版本对完成、带着运行时原因失败、或者已取消。它在事务启动之前打开，在事务结束之时关闭，所以一次点击在同一轮交互里就有回应。卡片本身由标题栏 chrome 渲染器绘制，该渲染器本来就拥有一块位于两个内容表面之上的原生矩形，而 Electron 主进程给这块矩形的是卡片自身的尺寸而不是窗口的尺寸，所以更新运行期间 Harness 与 Chat 表面仍然接收指针。卡片在内容区水平居中，其垂直中心位于内容高度的约三分之一处，与"版本未变化"时那个原生结果对话框出现的位置一致，而不是窗口的几何正中。

决定什么是真实的，是运行时而不是视图。[`managed-harness.ts`](../../../../apps/desktop/src/managed-harness.ts) 在进入每个阶段时报告该阶段，并附带该阶段是否可停止，视图只做转发，不添加任何一项。`busy` 现在覆盖整个 staging 事务，而不再只是注册表读取之后的部分，这正是防止菜单把第二个事务排到第一个之后的原因。

## Stages a transaction can prove

`preparing` 是注册表往返与持久的 pending 标记，`installing` 是包管理器子进程，`verifying` 是把暂存的清单、版本、完整性与入口和已解析的发布做比对，`health` 用一个一次性的 Harness home 启动候选版本。这四个就是事务本来会按本来顺序调用的四步，诊断日志一直以来命名的也正是它们。

下载不是独立阶段。取得官方发布靠的是一个 `npm install` 子进程，它自行完成解析、取回和写入，不发出任何结构化事件，并且以 `--loglevel=error` 运行，所以它周围唯一可观察的边界是"启动"和"退出"。卡片的第二行因此说它正在下载并安装，那正是该子进程在做的事，而不是把一个进程按耗时猜测拆成两个状态。安装自身的输出尾部为诊断日志保留，绝不用于解析出展示状态。

完成只对运行时自身的保留状态声明：一个 promoted 结果，如果它的版本并不是当前正在使用的版本，就报告为失败并同时给出两个版本号，因为退出码为 0 不是用户在意的那个条件。

完成态卡片只有在正在使用的版本真的发生移动时才会给出「从哪个版本来」，因此对当前版本做重新安装绝不会被画成升级：来路版本是在事务开始之前读取的，而 `retained.previous` 保持它作为回滚目标的原有含义。同一张卡片会说明被提升的版本要在重启 Harness 后才生效，因为在那次重启之前，活动进程仍然在服务旧版本。

## Cancellation

取消在 `preparing` 与 `installing` 被接受，在 `verifying` 与 `health` 被拒绝；这个判定只在运行时内部产生一次，并作为数据传给卡片，所以一个控件不可能宣传事务并不提供的安全性。

可接受的两个阶段是不向 staging 目录之外写入任何东西的两个阶段。包管理器被 `--prefix` 限制在该目录内，两个 npm 配置槽指向桌面外壳拥有的空文件，`--ignore-scripts` 意味着没有子进程会存活下来写到别处，所以放弃该子进程只丢弃一个候选版本，被提升的程序目录完全未被动过——这与运行时已经为它实现的崩溃恢复所到达的终态相同，只是不必等待该子进程自己的 15 分钟上限。提升本身是一对重命名加一次原子状态写入，任何取消都不会试图打断它。

被拒绝的阶段就是提升闸门：候选版本已经被取回，在它对判定的中间和重命名之间停下来只会浪费一次健康检查，换不到任何安全。在那里卡片的红色控件变灰、保持可点击，并说明它为何不采取行动，而不是无声地失效。

取消请求在发出之前会先确认，而被运行时拒绝的取消不会被呈现为已经发生的取消。卡片也可以在事务继续时收起，收起会把它所占据的标题栏控件交还给外壳；收起的卡片仍然会带着事务结果重新出现。

## Alternatives considered

**解析包管理器输出以得到下载进度。** npm 的人类可读进度行不是协议：它们随 npm 自己的小版本变化，随附的参数会在配置的日志级别上抑制它们，而且它们不携带任何完成条件。把这类行映射成阶段的界面会显得权威，并在包管理器改动的措辞的任何时刻出错，而这正是本任务禁止的失败模式。

**用计时器推进阶段。** 定时推进报告的是分钟数流逝，不是工作，并且会为一个已经在注册表读取中失败的事务显示"正在安装"。卡片只发布运行时报告的阶段和每个结果一个终止状态，所以不存在不是由某个步骤引起的转换。

**为卡片单独开一个无边框窗口。** 第二个 `BrowserWindow` 拥有自己的文档、preload、IPC 面、打包条目，以及跟随父窗口的缩放与移动几何。标题栏 chrome 已经是桌面外壳拥有的、位于两个内容表面之上的渲染器，背后还有一个纯函数、已测试的矩形解析器；新开一个窗口会为了到达同一个层级而把这些全部复制一遍。

**在任何用户要求的阶段杀掉包管理器。** staging 目录让这成为可承受的而非破坏性的，但提升闸门正是事务关于候选版本的证据所在，而且本任务的默认就是不中断安装与验证。在那里拒绝所花费的是至多一次有上限的健康检查。

**让卡片在更新期间阻塞整个窗口。** chrome 表面协议已经有一个用于短暂确认的整内容 `dialog` 状态，复用它会把指针从 Harness 上取走整个安装的时长。改用卡片尺寸的矩形，代价是卡片出现时模式切换让位，换来窗口其他每一个像素都仍然可用。

**也给回滚显示卡片。** 回滚只对被保留的版本做健康检查并交换两个状态字段，所以它没有卡片所绘制的任何阶段，它的圆点行会乱序点亮。它保持现有行为：菜单报告为忙碌，原生对话框报告其结果。

## Consequences

启动更新的用户现在会在同一次交互里看到一个状态，而一个不可中断的事务会说明这一点，而不是看起来卡住了。卡片的主张全部是运行时本来就知道的事情，所以这个界面不会比事务更久或与事务矛盾，并且离开运行状态的路径每一条都是已定结果：提升、失败、取消或未变化。

它的代价：模式切换在标题栏中让位于卡片，因为卡片的矩形正是这些控件本来绘制的位置，而卡片不能被一个菜单盖住。下载与安装仍然算作一个报告步骤。取消的安装会放弃已经取回的字节，而在注册表往返仍在飞行中时于 `preparing` 接受的取消，会在该往返被放弃时才生效，而不是在它存在之前就生效。卡片覆盖安装、更新与重新安装；Harness 标签页的首次设置按钮保持它自己的路径，所以它仍然只报告失败，而回滚仍然通过原生对话框报告。
