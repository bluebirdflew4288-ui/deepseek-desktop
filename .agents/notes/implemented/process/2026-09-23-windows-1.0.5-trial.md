# Agent Note: Windows 1.0.5 local trial and release boundary

Status: implemented

English | [中文](2026-09-23-windows-1.0.5-trial.zh.md)

## Problem

The Windows 1.0.5 build needed a real local installation and user trial to establish its desktop and managed Harness behavior. Trial acceptance and public release readiness are separate decisions: the installed artifacts were unsigned, and signing and GitHub publication have not been completed.

## Decision

The user has accepted the Windows 1.0.5 local trial. The trial used unsigned per-user NSIS and ZIP artifacts and a managed Harness update to 0.1.5-rc.3. This acceptance does not represent a signed or public release. No trusted Windows signing certificate is currently available, so a formal Windows release remains blocked; do not describe the unsigned trial artifacts as signed or released.

The original checkout and its uncommitted changes, user profile, Chat data, Memory data, cookies, and sessions were preserved. The app's logged removal of a manually preserved rc.2 backup is a confirmed trial incident; no agent command caused that deletion. Follow-up Harness retention work therefore preserves unreferenced version directories rather than automatically deleting them.

## Alternatives considered

**Publish the unsigned installer as the formal Windows release.** Rejected because no trusted signing identity is available and the user requested signed release artifacts.

**Treat synthetic boot or a successful package build as equivalent to the local trial.** Rejected because the user exercised the installed app and provided the trial acceptance; several individual flows remain unverified and are documented below.

## Consequences

The Windows local trial is accepted, and its evidence remains useful for future maintenance. Signing, upload, tag, and public GitHub Release remain incomplete. The installer/ZIP are unsigned; npm staging install, Chat authentication, tray/notification edge cases, and several post-update UI flows were not qualified by this trial. Unreferenced managed-version directories may use additional disk space because automatic deletion cannot distinguish them from copied user backups.

## Verification

- Windows/Desktop/Harness targeted suite: 14 files, 232 passed, 2 skipped. The skipped tests assert POSIX SIGTERM handler delivery and escalation; Windows Node does not promise JavaScript SIGTERM delivery. A Windows-specific abort test verifies that the owned child exits.
- Desktop TypeScript check, including test TypeScript: passed.
- Targeted pairing checks passed for the root README, Desktop README, Windows trial note, and this trial record. At the time of the trial, the full-corpus pairing check was blocked by the pre-existing, unchanged `docs/config-catalog.md` / `.zh.md` code-block mismatch.
- The disposable old-version-unified package tree booted the synthetic profile and printed a local listener URL. An unauthenticated request reached the HTTP token fence and returned 401. No Chat credentials were entered.
- A fresh npm staging install with the overrides remained empty after about 51 seconds with no output; its owned process was stopped. The npm install/lockfile path is therefore unverified.

## Trial observations and limits

- Installed executable hash: `CCA2517AF3889E512FBAF86A0BD8D7C2DDC024CD0C085FB5179185464B2DA2CD`; installed `app.asar` matches the build hash in the artifact table. HKCU Uninstall reports DeepSeek Desktop `1.0.5`.
- Before the managed update, the default profile's Harness tab loaded on `127.0.0.1:53065` without the `_await` error. F10 opened the native menu with Memory, Harness, Settings, and Quit; the Harness submenu showed `0.1.5-rc.2` as available. The Chat sign-in page and Windows notification settings were visible. No Chat credentials were entered.
- The user initiated the built-in update. The update card visibly showed the downloading/installing stage and advised keeping the app open. No explicit safe Cancel action was visible, so the app remained open until its transaction completed.
- Managed Harness logs record `update` phases `resolved`, `staging`, `health`, and `promoted` for `0.1.5-rc.3`. `state.json` then reported current `0.1.5-rc.3`, previous `0.1.5-rc.2`. The app's garbage-collection log recorded removal of `0.1.5-rc.2.rollback-20260923`, the manually preserved original mixed-tree backup. No agent command removed it. Both `0.1.5-rc.2` and `0.1.5-rc.3` version directories remained; the rc.2 rollback directory did not.
- Independent synthetic boot of the exact copied stage tree was rejected by execution policy before process creation and was not retried. The successful synthetic boot evidence belongs to the earlier healthy temporary clone, not that exact stage directory. The app's later built-in update transaction recorded its own health phase before promotion.
- The promoted rc.3 root packages are Cordis `4.0.2` and loader `1.0.3`. The app-owned process listened on `127.0.0.1:55150`; an unauthenticated GET to `/` returned HTTP 401, confirming the service reached its token fence. The earlier port `53065` was no longer listening. This does not independently verify every Harness UI interaction after the update.
- The user reports that the current UI looks normal and has accepted the local trial. Computer Use was unavailable to the agent for a fresh post-update visual inspection. Tray restore/exit, notification delivery and click routing, unread transitions, and update cancellation remain unverified. The update card's downloading/installing stage was observed before promotion.
- The original checkout at `..\deepseek-desktop` and its uncommitted changes remain untouched. The 1.0.4 installer remains in that checkout at `apps/desktop/dist/DeepSeek Desktop Setup 1.0.4.exe` (SHA-256 `7684512B91B711E1843C142262C08AD0A247D99BCED22907767BAC4E50B505DB`). No `.dsh` configuration, Chat, Memory, cookies, or session data was intentionally edited or cleaned. The initial 1.0.5 launch did cause `prepareProfile()` to rewrite the empty web `cordis.yml` as previously recorded.
- Fresh npm staging remains unverified because the install attempt stalled. The promoted rc.3 tree has runtime evidence from its update health phase and the live unauthenticated 401 probe. No push, tag, GitHub Release, signature, or public distribution occurred.

## Resume boundary

The prior mixed rc.2 tree was removed from the manually created rollback path by the app's GC during this trial. Before another update or reinstall, verify the precise target version and establish a new verified program-tree backup. Do not edit or clean the `.dsh` profile or user data. Chat authentication remains unqualified for release; inspect external origins and trust prompts before any login.
